# Forensics Κοντέινερ (Container Forensics)

> 🇬🇷 Ελληνική έκδοση του [Lab 09 — Container Forensics](../../Lab%2009/README.md)

Τα κοντέινερ (containers) έχουν επαναστατήσει τον σύγχρονο τρόπο ανάπτυξης λογισμικού, επιτρέποντάς μας να κατασκευάζουμε και να αναπτύσσουμε εφαρμογές με ταχύτερο και πιο αξιόπιστο τρόπο. Έτσι, η λεγόμενη *containerization* — δηλαδή η συσκευασία μιας εφαρμογής μαζί με ό,τι χρειάζεται για να τρέξει — έχει γίνει όλο και πιο δημοφιλής τα τελευταία χρόνια. Όπως όμως και κάθε άλλη τεχνολογία, τα κοντέινερ δεν είναι ασφαλή από κίνδυνους και ευπάθειες ασφαλείας. Μπορούν επίσης να χρησιμοποιηθούν από εγκληματίες για κακόβουλους σκοπούς, όπως η φιλοξενία malware ή η διεξαγωγή οποιασδήποτε άλλης παράνομης δραστηριότητας.

Γιατί μας ενδιαφέρει ως ερευνητές ψηφιακής forensic; Στο πραγματικό κόσμο, κοντέινερ χρησιμοποιούνται συχνά για την εκτέλεση υπηρεσιών που εκτίθενται στο Internet, οπότε ένας επιτιθέμενος μπορεί να τα καταλάβει για να φιλοξενήσει κακόβουλο κώδικα, να οργανώσει επιθέσεις ή να εκμεταλλευτεί τον υπολογιστικό ισχύ για εξόρυξη κρυπτονομισμάτων (cryptojacking). Σε μια διερεύνηση (incident response) θα πρέπει λοιπόν να μπορούμε να αποκτήσουμε, να αναλύσουμε και να κατανοήσουμε τα στοιχεία που άφησαν πίσω τους τα κοντέινερ.

Στο συγκεκριμένο εργαστήριο, θα κατανοήσουμε τα θεμελιώδη των κοντέινερ και, στη συνέχεια, θα εξερευνήσουμε τα εργαλεία και τις τεχνικές που μπορούμε να χρησιμοποιήσουμε για να διεξάγουμε ερευνές σε περιβάλλοντα με κοντέινερ (containerized environments), ώστε να εντοπίσουμε πιθανές απειλές ασφαλείας και κακόβουλη δραστηριότητα.

> ⚠️ Προσοχή: Σε πραγματικές διερευνήσεις, κάθε πρόσβαση σε κοντέινερ, εικόνες (images) ή τον υπολογιστή οικοδεσπότη (host) πρέπει να γίνεται με ρητή άδεια και με τήρηση της αλυσίδας διακράτησης (chain of custody), δηλαδή με καταγεγραμμένη ακολουθία όσων αγγίξατε και πότε. Σε αυτό το εργαστήριο δουλεύουμε σε τοπικό, ελεγχόμενο περιβάλλον και αποκτούμε μόνο αντίγραφα για ανάλυση.

## Κοντέινερ — Τι είναι;

> Τα κοντέινερ είναι πακέτα λογισμικού που περιέχουν όλα τα απαραίτητα στοιχεία για να εκτελεστούν σε οποιοδήποτε περιβάλλον. Με αυτόν τον τρόπο, τα κοντέινερ υπερβαίνουν (virtualize) το λειτουργικό σύστημα και εκτελούνται παντού — από ένα ιδιωτικό κέντρο δεδομένων (private data center) μέχρι το δημόσιο cloud ή ακόμη και στο προσωπικό laptop ενός προγραμματιστή. Από το Gmail μέχρι το YouTube και την Αναζήτηση, όλα όσα τρέχουν στη Google εκτελούνται σε κοντέινερ.
> 
> — [Google Cloud](https://cloud.google.com/learn/what-are-containers#section-1)

Με λίγα λόγια, ένα κοντέινερ μοιάζει με ένα «πακέτο» μιας εφαρμογής που έχει ό,τι χρειάζεται για να τρέξει: τον κώδικα και τις ρυθμίσεις της εφαρμογής, καθώς και τις εξαρτήσεις (dependencies) και τις βιβλιοθήκες (libraries) που απαιτούνται. Σε αντίθεση με μια εγκατάσταση που κάνετε «χειροκίνητα» στο σύστημά σας, το πακέτο αυτό είναι επαναλήψιμο (reproducible): ό,τι δουλεύει σε έναν υπολογιστή, δουλεύει το ίδιο και σε έναν άλλον.

### Παράδειγμα

Φανταστείτε ότι αναπτύσσετε μια εφαρμογή και ο κώδικας χρειάζεται μια συγκεκριμένη έκδοση μιας γλώσσας προγραμματισμού και συγκεκριμένες βιβλιοθήκες για να εκτελεστεί. Θα μπορούσατε να τις εγκαταστήσετε στον δικό σας υπολογιστή, αλλά αυτό θα μπορούσε να δημιουργήσει συγκρούσεις (conflicts) με άλλες εκδόσεις της γλώσσας ή των βιβλιοθηκών που ενδέχεται να έχετε ήδη εγκαταστήσει. Ακόμη κι αν καταφέρετε να επιλύσετε όλες τις συγκρούσεις στον υπολογιστή σας, μπορεί να αντιμετωπίσετε παρόμοιες συγκρούσεις στον διακομιστή όπου θα αναπτύξετε (deploy) την εφαρμογή σας.

Εναλλακτικά, θα μπορούσατε να συσκευάσετε την εφαρμογή και τις εξαρτήσεις της σε ένα κοντέινερ, το οποίο θα εκτελέσει την εφαρμογή με τις απαιτούμενες εκδόσεις της γλώσσας προγραμματισμού και των βιβλιοθηκών, χωρίς καμία σύγκρουση με εκείνες που είναι εγκατεστημένες στον υπολογιστή οικοδεσπότη. Στη συνέχεια θα μπορούσατε να μεταφέρετε αυτό το κοντέινερ σε άλλον υπολογιστή ή διακομιστή, και η εφαρμογή θα εκτελέσται ακριβώς όπως έτρεχε και στον δικό σας υπολογιστή.

> 💡 Συμβουλή: Αυτή η ιδιότητα — «το ίδιο περιβάλλον παντού» — είναι χρήσιμη και στην forensic. Όταν θέλετε να ξαναπαράγετε μια ύποπτη συμπεριφορά, μπορείτε να ξεκινήσετε την ίδια βασική εικόνα (base image) με εκείνη του υπόπτου και να μελετήσετε τι αλλάζει — χωρίς να «μολύνετε» τις αρχικές σας εικόνες.

### Κοντέινερ και VM — Ποια είναι η διαφορά;

> Ίσως γνωρίζετε ήδη τις μηχανές υπολογιστές (VMs): ένα λειτουργικό σύστημα επισκέπτη (guest operating system) όπως Linux ή Windows εκτελείται πάνω από ένα λειτουργικό σύστημα οικοδεσπότη (host) με πρόσβαση στο υποκείμενο υλικό. Τα κοντέινερ συγκρίνονται συχνά με τις μηχανές υπολογιστές (virtual machines — VMs). Όπως και οι VM, τα κοντέινερ σάς επιτρέπουν να συσκευάσετε την εφαρμογή σας μαζί με βιβλιοθήκες και άλλες εξαρτήσεις, παρέχοντας απομονωμένα περιβάλλοντα για την εκτέλεση των υπηρεσιών λογισμικού σας.
> 
> — [Google Cloud](https://cloud.google.com/learn/what-are-containers#section-4)

Για να δείτε πιο λεπτομερώς τις διαφορές, ρίξτε μια ματιά σε [αυτό το άρθρο](https://www.ibm.com/cloud/blog/containers-vs-vms).

**Θεωρητικό υπόβαθρο (γιατί μας ενδιαφέρει στην forensic):** Σε μια VM, κάθε εικόνα λειτουργικού συστήματος έχει τον δικό της πλήρη πυρήνα (kernel) που τρέχει πάνω σε έναν hypervisor. Σε ένα κοντέινερ, αντίθετα, όλα τα κοντέινερα του ίδιου υπολογιστή μοιράζονται **τον ίδιο πυρήνα** του οικοδεσπότη· η απομόνωση γίνεται μέσω μηχανισμών του ίδιου πυρήνα, όπως τα *namespaces* (κάνουν το κοντέινερ να «βλέπει» μόνο του ορισμένους πόρους) και τα *cgroups* (περιορίζουν τη χρήση CPU/μνήμης), και στηρίζεται σε ένα *union filesystem* διαφανών επιπέδων (layers). Αποτέλεσμα: τα κοντέινερ είναι πολύ πιο ελαφρά και γρήγορα από τις VM, αλλά δεν αποτελούν «μικρομηχανές» πλήρους απομόνωσης.

Αυτή η διαφορά έχει άμεσες συνέπειες για την έρευνα: τα κοντέινερ δεν είναι ανεξάρτητοι μηχανές — τα στοιχεία τους βρίσκονται στο σύστημα του υπολογιστή οικοδεσπότη (αρχεία, καταγραφές του Docker, δικτυακές συνδέσεις), οπότε μερικές φορές πρέπει να «βγείτε» από το κοντέινερ και να εξετάσετε το host. Και το αντίστροφο ισχύει: από το host μπορείτε να δείτε μέσα στα κοντέινερ.

> ⚠️ Προσοχή: Επειδή τα κοντέινερ μοιράζονται τον πυρήνα του host, μια ευπάθεια στον πυρήνα ή στον ίδιο τον engine των κοντέινερ μπορεί να επιτρέψει σε επιτιθέμενο να «δραπετεύσει» από το κοντέινερ και να αποκτήσει πρόσβαση στο σύστημα οικοδεσπότη (αυτό ονομάζεται *container escape*). Σε μια διερεύνηση, μην περιορίζεστε στο εσωτερικό του κοντέινερ· εξετάστε πάντα και το host.

### Τι είναι το Docker;

Το Docker είναι ένα εργαλείο οργάνωσης (orchestration) κοντέινερ που μας βοηθά να διαχειριστούμε ολόκληρο τον κύκλο ζωής των κοντέινερ, όπως η χτίση (build), η εκτέλεση (run) και η τερματισμός τους. Αναφέρεται επίσης μερικές φορές ως «μηχανή κοντέινερ» (container engine) ή «περιβάλλον εκτέλεσης κοντέινερ» (container runtime), και υπάρχουν και άλλα παρόμοια εργαλεία όπως τα Podman, Cri-o, Runc, Containerd κ.λπ. που προσφέρουν παρόμοιες λειτουργίες.

Δύο βασικές έννοιες που θα συναντήσουμε συχνά:

- **Εικόνα (image):** το αναλλοίωτο (read-only) πρότυπο που περιέχει το σύστημα αρχείων και τις ρυθμίσεις. Οι εικόνες χτίζονται σε «στοίβα» από επίπεδα (layers) και μπορούν να αποθηκευτούν σε ένα ταμείο εικόνων (registry), όπως το Docker Hub.
- **Κοντέινερ (container):** η εκτελούμενη παρουσίαση μιας εικόνας — δηλαδή η εικόνα «σε δράση», με τη δική της ζωή (ξεκίνησε, σταμάτησε, τερμάτισε) και τις δικές της αλλαγές αρχείων.

Ο Docker αποθηκεύει τα δεδομένα των εικόνων και των κοντέινερ στον δίσκο του υπολογιστή οικοδεσπότη (προεπιλεγμένα κάτω από το `/var/lib/docker/`) — και γι' αυτό, όπως θα δούμε, πολλά στοιχεία μπορούν να ανακτηθούν ακόμη κι αν ένα κοντέινερ έχει σταματήσει.

> 💡 Συμβουλή: Μην συγχέετε «εικόνα» και «κοντέινερ». Η εικόνα είναι το πρότυπο (δεν αλλάζει), το κοντέινερ είναι η εκτελούμενη εικόνα που μπορεί να τροποποιήσει αρχεία και να καταγράψει ενέργειες. Στην έρευνα, αυτό μας δίνει δύο διαφορετικές πηγές στοιχείων: τι έφτασε στο σύστημα (εικόνα) και τι συνέβη κατά την εκτέλεση (κοντέινερ).

## Απόκτηση Αποδεικτικού Υλικού (Evidence)

Στο πλαίσιο της forensic κοντέινερ, το αποδεικτικό υλικό (evidence) μας θα αποτελείται κυρίως από κάθε πληροφορία που μπορούμε να αποκτήσουμε από κοντέινερ — είτε εκτελούμενα είτε σταματημένα — από εικόνες κοντέινερ, καταγραφές (logs) κοντέινερ, καταγραφές του runtime/engine των κοντέινερ και άλλα. Υπάρχουν αρκετοί τρόποι να αποκτήσουμε στοιχεία που σχετίζονται με ένα κοντέινερ, όπως η εξαγωγή του συστήματος αρχείων του, ο έλεγχος των διαφορών μεταξύ του κοντέινερ και της βασικής του εικόνας, η επιθεώρηση των μεταδεδομένων και των ρυθμίσεων ενός κοντέινερ, η προβολή των καταγραφών του, ο έλεγχος του ιστορικού της εικόνας και η απόκτηση ενός memory dump των διεργασιών που εκτελούνται μέσα στο κοντέινερ. Ας εξερευνήσουμε λοιπόν καθέναν από αυτούς τους τρόπους ξεχωριστά:

> 💡 Συμβουλή: Λάβετε υπόψη τη σειρά ευθραυστότητας (volatility): τα στοιχεία στη μνήμη είναι πιο εύθραυστα από τα στοιχεία στον δίσκο και χάνονται μόλις σταματήσει η διεργασία. Πρακτικά, αυτό σημαίνει ότι πρέπει να σχεδιάσετε την απόκτηση από πριν — να καταγράψετε τι τρέχει, να αποκτήστε τα ευρήματα με τη σειρά τους (μνήμη, μετά δίσκος/καταγραφές) και να κρατάτε σημειώσεις για κάθε ενέργειά σας.

### Εξαγωγή Συστήματος Αρχείων (Filesystem Export)

Ένας τρόπος να αποκτήσουμε στοιχεία είναι να εξάγουμε το σύστημα αρχείων ενός κοντέινερ ως αρχείο tar.

Για να δείξουμε τη διαδικασία, ας ξεκινήσουμε ένα κοντέινερ:

```
$ docker run -it alpine sh
/ # ls
bin    dev    etc    home   lib    media  mnt    opt    proc   root   run    sbin   srv    sys    tmp    usr    var
```

Μέσα στο κοντέινερ, ας δημιουργήσουμε ένα αρχείο με όνομα `hello_world` που να περιέχει το κείμενο "Hello, World!":

```
#/ echo "Hello, World!" > hello_world
```

Στη συνέχεια, κρατώντας το κοντέινερ να εκτελείται, ανοίξτε ένα ακόμη τερματικό και ελέγξτε το αναγνωριστικό (ID) του κοντέινερ:

```
$ docker ps --all
CONTAINER ID   IMAGE            COMMAND                  CREATED         STATUS                     PORTS     NAMES
87908a159c5b   alpine           "sh"                     6 minutes ago   Exited (0) 6 minutes ago             agitated_matsumoto
```

Τώρα, ας εξάγουμε το σύστημα αρχείων του κοντέινερ ως αρχείο tar:

```
$ docker export 87908a159c5b -o output.tar
```

Μπορούμε στη συνέχεια να εξαγάγουμε το σύστημα αρχείων και να επιβεβαιώσουμε ότι το αρχείο `hello_world` παρουσιάζεται εκεί, εκτελώντας τις ακόλουθες εντολές:

```
$ mkdir output

$ tar -xf output.tar -C output

$ ls -la output
```

> 💡 Συμβουλή: Το `docker export` εξάγει το **σύστημα αρχείων ενός κοντέινερ** (και όχι μια εικόνα μαζί με τα επίπεδά της). Αν χρειαστείτε να εξάγετε μια **εικόνα** ως αρχείο tar μαζί με τη δομή των layers της, χρησιμοποιήστε `docker save`. Είναι δύο διαφορετικές εντολές με διαφορετικά ευρήματα — μην τις συγχέετε στην έρευνα.

> 💡 Συμβουλή: Εργαστείτε πάντα σε αντίγραφα του εξαγόμενου tar. Η ανάλυση πάνω στο αρχικό, ζωντανό κοντέινερ γράφει νέα δεδομένα και μπορεί να τροποποιήσει ή ακόμη και να καταστρέψει στοιχεία. Επίσης, οι χρόνοι αρχείων (timestamps) που βλέπετε στο `ls -la` προέρχονται από την εικόνα/το κοντέινερ και μπορούν να χρησιμεύσουν στο χτισμό χρονολογίου (timeline) του περιστατικού.

### Εντοπισμός διαφορών μεταξύ Κοντέινερ και Βασικής Εικόνας

Αυτό περιλαμβάνει τη σύγκριση της τρέχουσας κατάστασης ενός εκτελούμενου ή σταματημένου κοντέινερ με τη βασική του εικόνα (base image), ώστε να εντοπιστούν οι αλλαγές που έγιναν. Είναι ιδιαίτερα χρήσιμο στον εντοπισμό αλλαγών που ενδέχεται να έχουν γίνει στο κοντέινερ από malware ή από μη εξουσιοδοτημένη οντότητα.

Θυμηθείτε ότι μια εικόνα αποτελείται από στοίβα επιπέδων (layers) και όταν ξεκινά ένα κοντέινερ, οι τροποποιήσεις δεν αλλάζουν τη βασική εικόνα (είναι αναλλοίωτη), αλλά καταγράφονται σε ένα νέο, προσαρτημένο επίπεδο αλλαγών. Το `docker diff` μας δείχνει ακριβώς αυτές τις αλλαγές.

Ένας τρόπος να εντοπίσουμε τις διαφορές είναι χρησιμοποιώντας την εντολή `docker diff`, και σύμφωνα με την τεκμηρίωση του Docker, καταγράφονται τρεις τύποι αλλαγών:

| Σύμβολο | Περιγραφή |
| --- | --- |
| A | Προστέθηκε ένα αρχείο ή κατάλογος |
| D | Διαγράφηκε ένα αρχείο ή κατάλογος |
| C | Τροποποιήθηκε ένα αρχείο ή κατάλογος |

Μπορούμε να το δοκιμάσουμε στο κοντέινερ που δημιουργήσαμε στο προηγούμενο παράδειγμα:

```
$ docker diff 87908a159c5b
C /root
A /root/.ash_history
A /hello_world
```

Όπως φαίνεται στην έξοδο, ο κατάλογος `/root` τροποποιήθηκε, προστέθηκε ένα νέο αρχείο με όνομα `/root/.ash_history` (το οποίο δημιουργήθηκε αυτόματα όταν εκτελέσαμε την πρώτη μας εντολή μέσα στο κοντέινερ), καθώς και η προσθήκη του αρχείου `/hello_world` που δημιουργήσαμε.

> 💡 Αξίζει να σημειωθεί ότι το προεπιλεγμένο shell της Alpine είναι το `sh`-συμβατό `ash`, οπότε το αρχείο ιστορικού ονομάζεται `.ash_history` αντί για `.sh_history`, παρόλο που ορίσαμε `sh` στην εντολή `docker run` μας.

> 💡 Συμβουλή: Αρχεία ιστορικού εντολών shell (όπως `.ash_history`, `.bash_history`) είναι τιμιότατα στοιγρά — μας δείχνουν τι πληκτρολόγησε ο χρήστης μέσα στο κοντέινερ. Πάντως, να θυμάστε ότι μπορούν και να μην υπάρχουν· δεν καταγράφεται ό,τι εκτελέστηκε μέσω εντολών χωρίς interactivity ή εντολών που σβήστηκαν. Μην βασίζεστε ποτέ σε μία μόνο πηγή στοιχείων.

### Επιθεώρηση Μεταδεδομένων και Ρυθμίσεων Κοντέινερ

Η επιθεώρηση της ρύθμισης ενός κοντέινερ περιλαμβάνει την εξέταση των λεπτομερειών ρύθμισης ενός κοντέινερ, όπως οι ρυθμίσεις δικτύωσης, οι μεταβλητές περιβάλλοντος (environment variables) και η ρύθμηση αποθήκευσης.

Ένας τρόπος να επιθεωρήσουμε τη ρύθμιση ενός κοντέινερ είναι χρησιμοποιώντας την εντολή `docker inspect`, η οποία παρέχει μια αναλυτική εικόνα της ρύθμισης και των μεταδεδομένων ενός κοντέινερ:

```
$ docker inspect 87908a159c5b

        "Created": "2023-04-12T00:47:25.919621316Z",
        "Path": "sh",
        "Args": [],
        "State": {
            "Status": "exited",
            "Running": false,
            "Paused": false,
            "Restarting": false,
            "OOMKilled": false,
            "Dead": false,
            "Pid": 0,
            "ExitCode": 0,
            "Error": "",
            "StartedAt": "2023-04-12T00:47:26.302842966Z",
            "FinishedAt": "2023-04-12T00:47:50.743670453Z"
        },
...
...
...
```

Μπορούμε να αξιοποιήσουμε την επιλογή `--format` για να εξαγάγουμε συγκεκριμένες πληροφορίες, όπως η διεύθυνση IP του instance:

```
$ docker inspect --format='{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' 87908a159c5b
172.17.0.2
```

Ή η διεύθυνση MAC του instance:

```
$ docker inspect --format='{{range .NetworkSettings.Networks}}{{.MacAddress}}{{end}}' 87908a159c5b
02:42:ac:11:00:02
```

Ή το αναγνωριστικό διεργασίας (process ID) του κοντέινερ στον υπολογιστή οικοδεσπότη:

```
$ docker inspect --format='{{.State.Pid}}' 87908a159c5b
27666
```

Μπορούμε επίσης να το επιβεβαιώσουμε εκτελώντας την εντολή `ps`:

```
$ ps -fp 27666
UID          PID    PPID  C STIME TTY          TIME CMD
root       27666   27646  0 07:54 pts/0    00:00:00 sh
```

> 💡 Συμβουλή: Το JSON αυτό είναι ένα από τα πιο πλούσια στοιγρά που μπορείτε να αποκτήσετε. Δώστε προσοχή στα χρονικά ξίσματα `Created`, `StartedAt` και `FinishedAt` (σε μορφή ISO 8601, δηλαδή ΗΜΕΡΑ/ΜΗΝΑΣ-ΗΜΕΡΑ ΏΡΑ:ΛΕΠΤΑ:ΔΕΥΤΕΡΑ με `Z` για UTC) — είναι το υλικό για το χτισμό ενός χρονολογίου (timeline) του περιστατικού. Το `ExitCode` σας λέει αν η εκτέλεση ήταν επιτυχής (0) ή όχι, ενώ το `Pid` συνδέει το κοντέινερ με μια συγκεκριμένη διεργασία του host — χρήσιμο, όπως θα δούμε, για το memory dump. Οι IP διευθύνσεις των κοντέινερ ανήκουν συνήθως σε εσωτερικά, προεπιλεγμένα δίκτυα του Docker (όπως το `172.17.0.0/16`) και μπορούν να σας δείξουν με ποιες υπηρεσίες επικοινωνούσε το κοντέινερ.

> ⚠️ Προσοχή: Οι ρυθμίσεις ενός κοντέινερ μπορούν να περιέχουν ευαίσθητες πληροφορίες, όπως κλειδιά ή μυστικά που ορίστηκαν ως μεταβλητές περιβάλλοντος. Καταγράψτε τα, αλλά φροντίστε να προστατεύσετε το αποδεικτικό υλικό που αποκτάτε (κρυπτογράφηση, πρόσβαση μόνο για την ομάδα), ώστε η ίδια η έρευνα να μην γίνει πηγή διαρροής.

### Προβολή Αρχείων Καταγραφής (Logs) του Κοντέινερ

Για να αναζητήσουμε εντολές που ενδέχεται να έχουν εκτελεστεί μέσα στο κοντέινερ, ή τις καταγραφές οποιασδήποτε υπηρεσίας που ενδέχεται να εκτελούνταν μέσα στο κοντέινερ, μπορούμε να αξιοποιήσουμε την εντολή `docker logs`:

```
$ docker logs 87908a159c5b
/ # ls
bin    dev    etc    home   lib    media  mnt    opt    proc   root   run    sbin   srv    sys    tmp    usr    var
/ # echo "Hello, World!" > hello_world
/ # exit
```

> 💡 Συμβουλή: Τα `docker logs` δείχνουν την έξοδο (stdout/stderr) της κύριας διεργασίας του κοντέινερ. Με την προεπιλεγμένη ρύθμιση του Docker, αυτές οι καταγραφές αποθηκεύονται στον δίσκο του host, μέσα στον φάκελο του κοντέινερ (κάτω από το `/var/lib/docker/containers/`), οπότε μπορείτε να τις αναζητήσετε και από εκεί αν το ίδιο το κοντέινερ έχει αφαιρεθεί. Επειδή όμως είναι αρχεία καταγραφών, μπορούν να περικοπούν (rotation) ή να χαθούν ανάλογα με τις ρυθμίσεις — σημειώστε την κατάσταση τους τη στιγμή της απόκτησης.

> 💡 Σημειώστε ότι στην έξοδο βλέπουμε κυριολεκτικά τις εντολές που πληκτρολογήθηκαν στο shell (`ls`, `echo ... > hello_world`, `exit`). Σε πραγματική διερεύνηση, οι καταγραφές μπορεί να περιέχουν εντολές εγκατάστασης κακόβουλου λογισμικού, επικοινωνίες με εξωτερικούς εξυπηρετητές (C2) ή λάθη που αποκαλύπτουν τη φύση της επίθεσης.

### Ελέγχος Ιστορικού της Εικόνας (Image History)

Ο έλεγχος του ιστορικού μιας εικόνας μπορεί να βοηθήσει στον εντοπισμό αλλαγών που έχουν γίνει σε αυτήν, συμπεριλαμβανομένων πιθανών κακόβουλων τροποποιήσεων ή της προσθήκης κακόβουλων αρχείων ή επιπέδων (layers). Είναι ιδιαίτερα χρήσιμο για να εξετάσετε αν μια εικόνα έχει παρεμβληθεί (tampered) αφού έγινε το αρχικό της build.

Αυτό μπορεί να γίνει χρησιμοποιώντας την εντολή `docker history`, η οποία εμφανίζει το ιστορικό μιας εικόνας σε αντίστροφη χρονολογική σειρά, δείχνοντας κάθε επίπεδο που προστέθηκε στην εικόνα:

```
$ docker history alpine --no-trunc
IMAGE                                                                     CREATED       CREATED BY                                                                                          SIZE      COMMENT
sha256:9ed4aefc74f6792b5a804d1d146fe4b4a2299147b0f50eaf2b08435d7b38c27e   13 days ago   /bin/sh -c #(nop)  CMD ["/bin/sh"]                                                                  0B        
<missing>                                                                 13 days ago   /bin/sh -c #(nop) ADD file:9a4f77dfaba7fd2aa78186e4ef0e7486ad55101cefc1fabbc1b385601bb38920 in /    7.04MB
```

> 💡 Συμβουλή: Διαβάστε την έξοδο από τα πιο πρόσφατα προς τα παλαιότερα. Η στήλη `CREATED BY` σας δείχνει την εντολή που δημιούργησε κάθε επίπεδο (συχνά μοιάζει με τις οδηγίες ενός Dockerfile, όπως `ADD` ή `CMD`), ενώ η στήλη `SIZE` δείχνει πόσα δεδομένα πρόσθεσε. Τα `<missing>` σημαίνουν απλώς ότι τα δεδομένα εκείνου του επιπέδου δεν είναι διαθέσιμα τοπικά στο σύστημα σας. Οι εντολές `ADD`/`COPY` εμφανίζουν το όνομα του αρχείου ή μια αναγνωριστική σφραγίδα του, όχι όμως και το περιεχόμενό του — γι' αυτό συνδυάζετε πάντα το `history` με άλλες τεχνικές.

### Απόκτηση Memory Dump Κοντέινερ

Η απόκτηση ενός memory dump της διεργασίας ενός κοντέινερ μπορεί να είναι χρήσιμη για την έρευνα της κατάστασης εκτέλεσής του (runtime state), τον εντοπισμό κακόβουλης δραστηριότητας ή την εξαγωγή μυστικών (secrets).

Μπορούμε να χρησιμοποιήσουμε εργαλεία όπως `dd`, `gdb` ή `gcore` για να αποκτήσουμε ένα memory dump της διεργασίας του κοντέινερ. Από αυτές τις επιλογές, θα χρησιμοποιήσουμε το `gcore`, το οποίο αναμένει ως είσοδο το αναγνωριστικό διεργασίας (process ID) (ρίξτε μια ματιά στην ενότητα επιθεώρησης μεταδεδομένων και ρυθμίσεων κοντέινερ):

```
$ sudo gcore 27666
warning: Target and debugger are in different PID namespaces; thread lists and other data are likely unreliable.  Connect to gdbserver inside the container.
0x00007f48fa0993c1 in ?? () from target:/lib/ld-musl-x86_64.so.1
Saved corefile core.27666
[Inferior 1 (process 27666) detached]
```

> 💡 Συμβουλή: Διαβάστε προσεκτικά τις προειδοποιήσεις των εργαλείων. Εδώ, η προειδοποίηση μας λέει ότι το `gcore` εκτελείται σε διαφορετικό (PID namespace) από αυτό του κοντέινερ, οπότε ορισμένα δεδομένα μπορεί να μην είναι απολύτως αξιόπιστα. Σε πραγματική έρευνα, τέτοιες προειδοποιήσεις σας λένε ότι ίσως χρειάζεται να εκτελέσετε το εργαλείο μέσα στο ίδιο το κοντέινερ ή να διασφαλίσετε ότι η απόκτηση έγινε σωστά — πάντα επαληθεύετε ότι λάβατε ό,τι ζητούσατε.

Αφού έχουμε το memory dump, μπορούμε να αναζητήσουμε ενδιαφέρουσες πληροφορίες, όπως μυστικά ή κακόβουλες συμβολοσειρές (strings). Για παράδειγμα, επειδή γράψαμε "Hello, World" σε ένα αρχείο μέσα στο κοντέινερ στην αρχή του εργαστηρίου, ας δοκιμάσουμε να το αναζητήσουμε χρησιμοποιώντας την εντολή `strings`:

```
$ strings core.27666 | grep "Hello, World"
echo "Hello, World!" > hello_world
echo "Hello, World!" > hello_world
```

> 💡 Τι κάνουν στην ουσία αυτές οι εντολές: το `strings` εξάγει τις «αναγνώσιμες» συμβολοσειρές από ένα δυαδικό αρχείο (εδώ το core file), και το `grep` φιλτράρει τις γραμμές που περιέχουν το όρισμα που μας ενδιαφέρει. Στην πράξη, αναζητάτε στη μνήμη κλειδιά, κωδικούς, διευθύνσεις ή οποιαδήποτε συμβολοσειρά αποκαλύπτει τη δραστηριότητα του κοντέινερ τη στιγμή του dump.

> ⚠️ Προσοχή: Το memory dump είναι εύθραυστο (volatile) στοιγρά — χάνεται μόλις σταματήσει η διεργασία — και η ίδια η απόκτηση του είναι κάπου επεμβατική, γιατί το εργαλείο «συνδέεται» στη ζωντανή διεργασία. Κάντε την όσο το δυνατόν νωρίτερα, καταγράψτε ακριβώς τι εκτελέσατε (εντολή, ώρα, PID), και κρατήστε αντίγραφο του core αρχείου ως αρχικό αποδεικτικό υλικό πριν ξεκινήσετε τυχόν ανάλυση πάνω του.

## Συμπέρασμα

Για να κλείσουμε, μάθαμε τα θεμελιώδη των κοντέινερ και εξερευνήσαμε αρκετές τεχνικές για τη διεξαγωγή forensic σε ένα περιβάλλον με κοντέινερ, αλλά είναι σημαντικό να σημειωθεί ότι υπάρχουν και άλλες τεχνικές, καθώς και εργαλεία που μπορούν να αυτοματοποιήσουν αυτές τις διαδικασίες. Ορισμένα από αυτά τα εργαλεία είναι το [docker forensics toolkit](https://github.com/docker-forensics-toolkit/toolkit), το [docker explorer](https://github.com/google/docker-explorer), το [container explorer](https://github.com/google/container-explorer) και το [docker layer extract](https://github.com/micahyoung/docker-layer-extract).

Με αυτά τα λόγια, αν σας ενδιαφέρει να βελτιώσετε τις γνώσεις σας για τα κοντέινερ και την ασφάλειά τους, σας προτείνω ανεπιφύλακτα να δείτε το βιβλίο [Container Security](https://www.oreilly.com/library/view/container-security/9781492056690/) της Liz Rice. Προσφέρει πολύτιμες οπτικές στον κόσμο της ασφάλειας κοντέινερ και είναι εξαιρετικό υλικό τόσο για αρχάριους όσο και για έμπειρους επαγγελματίες.

# Ασκήσεις

Για να ολοκληρώσετε την άσκηση, είναι σημαντικό πρώτα να κατανοήσετε τι κάνουν τα Dockerfiles. Μπορείτε να βρείτε την επίσημη τεκμηρίωση του Docker για τα Dockerfiles [εδώ](https://docs.docker.com/engine/reference/builder/).

Η εικόνα κοντέινερ με την οποία θα δουλέψετε χτίστηκε χρησιμοποιώντας το ακόλουθο Dockerfile:

```
FROM alpine:latest

RUN echo "flag{?????????}" > flag1.txt

COPY flag2-part1.txt flag2-part1.txt

ADD flag2-part2.txt flag2-part2.txt

ENV flag3 flag{?????????}

CMD ["sh", "-c", "echo flag{?????????}"]

# I don't know, this line got corrupted I guess, but I'm sure you'll figure it out
COPY ????????????????????????????????????

# Deleting my secrets, I'm sure nobody will be able to see them now :D
RUN rm flag1.txt flag2-part1.txt flag2-part2.txt
```

> 💡 Συμβουλή: Αναλύστε το Dockerfile οδηγία προς οδηγία και θυμηθείτε ότι κάθε εντολή που τροποποιεί την εικόνα προσθέτει ένα νέο, μόνιμο επίπεδο στη στοίβα της. Στη συνέχεια, εφαρμόστε βήμα-βήμα τις τεχνικές που περιγράψαμε παραπάνω στην παρεχόμενη εικόνα για να εντοπίσετε ό,τι κρύβεται μέσα της. Μην βιαζόστε να «τρέξετε» την εικόνα χωρίς πρώτα να συλλέξετε στοιχεία — η σειρά με την οποία εξετάζετε κάθε πηγή (ιστορικό εικόνας, ρυθμίσεις, σύστημα αρχείων, καταγραφές) μπορεί να επηρεάσει τι θα βρείτε.

Μπορείτε να κατεβάσετε την εικόνα του κοντέινερ μέσα στο tar αρχείο από [εδώ](files/secrets.tar). Περιέχει συνολικά 5 κρυφές σημαίες (flags) που πρέπει να βρείτε. Καλή επιτυχία!
